## 一、现状分析

### 1.1 工程规模

- 源码文件 **502 个**（Kotlin 304 + Java 198），约 **18,600 行**
- 基于成熟开源 Network Survey（Android 信号测量）二次深度定制
- 关键规模节点：
  - `services/NetworkSurveyService.java`：**3,847 行**，真实信号采集服务（CellInfoCallback 事件驱动 + 全网工参匹配）
  - `ui/main/NsMainScreen.kt`：460 行，主界面 + 抽屉
  - `ui/main/AppNavigation.kt`：589 行，导航路由

### 1.2 反复出问题的病灶：工参导入链路

用户连续多轮反馈同一问题：
1. 导入工参报错 **"导入失败：The coroutine scope left the composition"**
2. 「上传日志」显示 **0k**，误以为没有日志埋点
3. 手动选择字段对应列的需求未稳定满足

经服务器日志（`/www/wwwroot/rsrp.cn/nsrebuild/logs/log_2026-09-02T12-58-27-642Z.json`）确证：
```
App 版本 : 1.0.4 (104002)
设备     : samsung SM-S9370
日志     : 09-02 20:57:47.239 I/App: 启动 v1.0.4
```
用户确实已装 1.0.4 埋点版，AppLogger 有效（有启动日志），但导入流程一条 `EngParam` 日志都没有——**崩溃发生在导入链路内部，日志被吞、堆栈未落盘**。

### 1.3 三大根因（重写前）

| 编号 | 根因 | 表现 |
|------|------|------|
| **病根1** | 职责混杂 | CSV 解析、列映射、协程编排、Compose 状态、数据库、日志全部堆在 `EngineeringParamsScreen.kt`（482 行），UI 与逻辑不可分离、不可单测 |
| **病根2** | 协程绑定 Composable 生命周期 | `rememberCoroutineScope()` 随页面重建被取消 → 后台回写 `mutableStateOf` 抛 **"The coroutine scope left the composition"** |
| **病根3** | 异常吞掉 + 日志不可见 | `catch(e)` 拼成「导入失败」文案，堆栈未写盘；日志上传仅显示 0KB，无法定位 |

### 1.4 为什么不做「整库推倒重写」

- 18,600 行、502 文件的生产级工程，含已验证稳定功能：真实信号采集（3,847 行服务）、百度地图、Monet 动态主题、多通道更新、耗电优化、扇区渲染。
- 整库重写**无法在一个会话内回归验证**：信号采集准确度、地图可用性、扇区渲染正确性都需真机长时间实测。
- 因此采用**「分层架构重构」**（业界标准的"彻底重构"形态）：**保持全部对外行为不变，改进内部结构**。重构聚焦唯一反复出问题的「工参导入链路」，其余稳定模块不动。

## 二、重构目标

1. **根治病根2**：协程改用进程级作用域，彻底杜绝 `rememberCoroutineScope` 被取消导致的崩溃。
2. **根治病根1**：把工参链路拆成清晰分层（UI / ViewModel / 领域层 / 数据层 / 基础设施），职责归位、可单测。
3. **根治病根3**：异常不吞，记录带完整堆栈的日志；日志上传显示真实大小 + 内容预览，不再误判 0k。
4. **行为一致**：解析、入库、列映射、扇区渲染所消费的字段，与重写前完全一致。
5. **可验证**：领域层剥离 Android 依赖，可在 JVM 单测；真实工参数据全量回归。

## 三、目标架构（分层）

```
┌─────────────────────────────────────────────────────────────┐
│  UI 层（Compose）                                             │
│  EngineeringParamsScreen（只渲染 + 交互，不碰解析/协程/DB）     │
└───────────────────────────┬─────────────────────────────────┘
                            │ collectAsStateWithLifecycle
┌───────────────────────────▼─────────────────────────────────┐
│  ViewModel 层                                                │
│  EngineeringParamViewModel（UiState + viewModelScope）        │
│  编排：选文件→读表头/示例→列映射→解析入库→刷新列表              │
│  异常不吞：AppLogger.e(tag,msg,throwable) 记堆栈 + 转用户提示  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 调用（IO 线程）
┌───────────────────────────▼─────────────────────────────────┐
│  领域层（纯 Kotlin，无 Android 依赖，可 JVM 单测）              │
│  CsvParsingEngine（编码/分隔符/列匹配/校验/行解析）             │
│  ImportFieldSpec（字段规格 + 必填校验 + 缺失字段检测）          │
│  EngineeringParamRepository（数据仓库门面）                    │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  数据层                                                      │
│  EngineeringParamDbHelper（单例 SQLite，批处理事务）           │
└─────────────────────────────────────────────────────────────┘

  基础设施（横切）：AppScope(进程级作用域) · AppLogger(带堆栈) · SAF · GBK/UTF8
```

### 关键职责划分

| 层 | 职责 | 不做什么 |
|----|------|----------|
| UI 层 | 渲染状态、分发用户意图（选文件/映射/清空） | 不碰协程/解析/入库/日志 |
| ViewModel | 持有 UiState、编排协程、调 Repository | 不做具体解析，不持有 Composable |
| 领域层 | 纯逻辑（编码探测、列匹配、字段校验、行解析） | 不依赖 Android，不持有 DB 单例 |
| 数据层 | 读写 SQLite、事务、缓存 | 不做 UI/解析 |
| 基础设施 | 作用域、日志、SAF、编码工具 | — |

## 四、关键设计决策

### D1. 协程作用域：`viewModelScope` 替代 `rememberCoroutineScope`

- **决策**：ViewModel 用 `viewModelScope`（绑定 ViewModel 生命周期）。ViewModel 生命周期长于 Composable 组合，且独立于页面重组，**不会因离开组合被取消**，从根上消除 "The coroutine scope left the composition"。
- **对比**：旧版 `rememberCoroutineScope` 绑定 Composable，页面一旦离开/重建即取消，后台回写状态即崩溃。
- **说明**：早期尝试用 `AppScope`（进程级）更激进，但 `viewModelScope` 已满足"永不因组合离开取消"，且符合官方架构规范，故采用后者。`AppScope.kt` 保留为通用后备。

### D2. 日志策略：异常不吞 + 带堆栈

- **决策**：所有 `catch(e)` 均调用 `AppLogger.e(TAG, msg, e)`（写完整堆栈到 `filesDir/logs/app.log`），并把 `e.message` 转为用户可读提示写入 `UiState.message`。
- **效果**：下次失败，用户「上传日志」能带回完整堆栈，开发者可精准定位。
- **日志上传 UI**：打开即显示**真实字节数（KB/MB）** + **日志末端内容预览**（取末 600 字），不再显示 0k 造成"没埋点"假象。

### D3. 解析逻辑单一真源：`CsvParsingEngine`（纯 Kotlin）

- **决策**：原 `CsvParamParser.java`（反编译来的 Java）逻辑归位到 **`CsvParsingEngine.kt`**（Kotlin object，无 Android 依赖）。
- `CsvParamParser.java` 保留为**兼容门面**，对外静态签名不变，内部委托给引擎。所有调用方无感。
- **好处**：逻辑可 JVM 单测；编码探测/分隔符/列匹配/校验规则集中一处。
- **对外契约保持**：`parse(InputStream, Map)`、`readPreview(InputStream)`、`autoMap(List)`、`readHeaders(InputStream)` 全部保留。

### D4. 字段规格唯一真源：`ImportFieldSpec`

- **决策**：把 UI 里散落的 `PARAM_FIELDS` 常量提取为领域层 `ImportFieldSpec.FIELDS`（含字段列索引、显示名、是否必填）。
- UI 列映射对话框、ViewModel、校验逻辑全部引用它，**杜绝三处重复定义漂移**。
- 新增 `missingRequired(selection)`：检查必填字段是否都映射，供导入前校验。

### D5. 数据访问门面：`EngineeringParamRepository`

- **决策**：UI/ViewModel 访问工参数据的唯一入口，屏蔽 `EngineeringParamDbHelper` 细节。
- 方法：`readPreview(uri)`、`parseAndInsert(uri, mapping)`、`getAll()`、`clearAll()`、`getCount()`。
- 本层**不吞异常**，解析/入库失败上抛给 ViewModel。

### D6. 保护既有契约（风险封锁）

以下是**不动**的对外契约，避免破坏已验证功能：

| 组件 | 契约 | 处置 |
|------|------|------|
| `EngineeringParam.java` | POJO，被地图/信号采集/JDBC 反射消费 | **完全不动** |
| `EngineeringParamDbHelper` | `insertAll/getAll/clearAll/getByRange/getCount` 等 | 只保留，不重构内部 SQL |
| `TowerMapLibreViewModel.loadLocalEngineeringParams` | `helper.getByRange(...)` | 不涉及，消费字段不变 |
| `Application`/`AppLogger`/`UpdateChecker`/`LogUploader` | 启动/日志/更新/上传 | 不动 |
| `TowerSymbols`（扇区渲染） | azimuth/tilt 驱动 | 不涉及 |

## 五、边界情况（特殊处理）

| 边界情况 | 处理 |
|----------|------|
| **GBK 编码 CSV**（用户真实表为 GBK 非 UTF-8） | 引擎 `detectEncoding`：UTF-8 BOM→UTF-16LE/BE→UTF-8→表头含 `\uFFFD` 时回退 GBK |
| **分隔符不同**（逗号/分号/Tab/中文逗号） | `resolveHeaderLine` 后 `detectDelimiter` 按出现次数最多的选 |
| **表头千差万别（字段名不一致）** | 手动选列为主 + 关键词 `autoMap` 辅助；下拉项带「表头（示例值）」帮用户凭值认出列 |
| **「小区Id」歧义** | `matchColumn` 明确把 `小区id/cellid/小区标识/ci` 匹配到 **CI（列3）**，非扇区号（列5）——已修正的历史 bug |
| **必填字段缺失** | `isValidParam`：小区名/经纬度非0/频点非0/基站ID非0；`ImportFieldSpec.missingRequired` 在导入前拦截 |
| **文件为空 / 读不到流** | 引擎返回 `message="文件为空"`；Repository `openInputStream` 为 null 抛 `IllegalStateException` |
| **用户中途离开页面** | 协程用 `viewModelScope`，不取消，回写安全（根治病根2） |
| **日志被吞** | `catch` 中 `AppLogger.e(...)` 记堆栈 + `AppLogger.w(...)` 记警告，落盘 app.log |
| **SQLite 事务** | `insertAll` 用 `beginTransaction` 包裹，全有或全无 |
